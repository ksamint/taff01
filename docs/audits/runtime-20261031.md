# Runtime and dependency audit — 2026-10-31

Baseline: `55718da1637ef92c76b72e1c80f1b531aa9f6a64`. Local source, installed
dependencies and isolated Docker rehearsals only; no production access.

## Findings and changes

1. **P1: BullMQ shared an evicting, volatile Valkey.** `compose.prod.yaml:21`
   configured `allkeys-lru`, disabled AOF/RDB and had no volume. Evicting individual
   queue keys can break queue structures; restarting lost scheduled/waiting jobs.
   Changed to `noeviction`, AOF with `appendfsync everysec`, and a `valkey_data`
   volume. Rate-limit counters share this service and will also survive a restart.
   At the existing 256 MiB cap writes now fail rather than deleting queue keys;
   API rate limiting already denies on failed counts. Monitor memory capacity.

2. **P1: three production Nodemailer advisories.** Installed/locked `10.1.0`
   was affected by recipient parser disagreements. Updated only Nodemailer to the
   minimum patched same-major `10.1.4` (MIT-0); removed its obsolete `10.1.0`
   release-age exception. No unrelated dependency versions changed. The three
   findings are distinct parser cases fixed by one dependency update, not three
   independent application defects. Maintainer advisories identify `<10.1.4` as
   affected and `10.1.4` as patched:
   [nested comment](https://github.com/nodemailer/nodemailer/security/advisories/GHSA-8c8m-p3m8-cjg8),
   [group delimiter](https://github.com/nodemailer/nodemailer/security/advisories/GHSA-m943-m63m-w62w),
   [angle delimiter](https://github.com/nodemailer/nodemailer/security/advisories/GHSA-85x2-q946-cp5h).
   [Release](https://github.com/nodemailer/nodemailer/releases/tag/v10.1.4).
   Existing email transport tests and three real parser regression inputs pass.

3. **P1: restricted source permissions reached migration images.** A checkout
   staged with umask 077 could preserve root-owned unreadable migration files in
   `/app/migrations` while the image runs as `node`. The final migration COPY now
   applies `0555` to files/directories, preserving read-only root ownership while
   allowing the migrator to traverse/read them. There is a Dockerfile regression
   check; full image execution remains part of integrated release verification.

4. **P2: shutdown could hang or skip cleanup after rejection.** API cleanup ran
   only after a successful realtime close and an HTTP close callback; worker
   cleanup ran only after a successful worker close. Neither had a deadline or
   rejection handling. A small shared shutdown function drains once, attempts
   every dependency cleanup after a failure, reports a sanitized stage, and exits
   nonzero on failure or after 25 seconds. Compose gives API/worker 30 seconds.
   HTTP ingress now stops before waiting for requests; realtime closes in parallel.
   All drains settle before dependencies close, including when realtime rejects.
   A one-word `exec` in the server CMD makes Node signal delivery explicit;
   this is defensive, since some shells already optimize the final command.
   Tests exercise actual SIGTERM/SIGINT, rejected cleanup, and simulated hung
   drain/cleanup. The shared helper avoids maintaining two separate timeout and
   error-handling implementations; no shutdown configuration framework was added.

## Queue failure and idempotence evidence

`apps/worker/src/digests.ts` hashes user/schedule/preference-version into job IDs,
validates incoming payloads, retries three times with exponential backoff, and
leaves database due markers unchanged on enqueue failure. Exhausted failed jobs
are removed so a later scan can retry. `packages/core/src/notifications.ts:391`
locks person/preferences, checks the preference version and exact due marker,
creates digest/Inbox rows and advances the marker in one transaction.
`packages/db/src/schema.ts:910` enforces user/workspace/local-date uniqueness.
Existing PostgreSQL notification tests cover concurrent/retried jobs, stale
versions, downtime, and transaction rollback/retry; no duplicate logic was added.

Run `node scripts/valkey-rehearsal.mjs` from the repository root. It creates two
process-specific containers/volumes and removes them in `finally`. It checks:

- Waiting and delayed job identities, payloads, states, and scheduler survive an
  AOF restart and an RDB snapshot copied into a separate empty volume.
- A restored scheduler executes at least two occurrences; saved waiting/delayed
  jobs complete after restore (the delayed job is promoted for a short rehearsal).
- A 256 KiB memory headroom plus a 2 MiB attempted write produces OOM, with zero
  evictions, and existing queue state/payloads stay intact.

**Restore detail:** load an RDB-only backup with AOF disabled initially, then enable
AOF after loading. Starting with AOF enabled against an empty AOF directory did
not load the standalone snapshot in this rehearsal. AOF `everysec` can lose roughly
one second on a hard crash; due markers and idempotent generation permit rescans.
The rehearsal does not claim survival of host disk loss or broken storage.

## Pooling and inventory limits

`packages/db/src/index.ts:5` caps each SQL pool at ten. Installed Postgres.js
`src/index.js:150` creates an additional max-one connection pool for LISTEN.
Budget at most eleven connections per API plus ten per worker, with additional
migration/admin overlap. The bounded shared pool is reused; there is no evidence
requiring a pool architecture change in this audit. Production concurrency and
database capacity were not measured.

The generic architecture extractor remaps a root build context to the Dockerfile
directory, producing false `worker_deploy=deploy` from `compose.apuch.yaml`.
Use explicit workspace mappings for inventory; `deploy/` contains shared build
metadata, not another running service. Root scripts can be mapped as tooling.

One remaining gate limitation: `scripts/licence-gate.mts` strips parentheses before
evaluating AND/OR, so a future `(MIT OR GPL-3.0) AND GPL-3.0` expression could be
accepted incorrectly. No current installed dependency with this expression was
found. A fail-closed grouped-expression regression is recommended separately.

## Follow-up fault injection and tracked dependency patches

Run `node --import tsx packages/core/src/runtime-faults.mts`. This uses separate
process-owned PostgreSQL/Valkey containers and random private ports. Results are
written under `.local/audit/runtime-faults*` and the containers/volumes are removed.
The optional `FAULT_BASELINE_DRIVER` points to an unmodified Postgres.js entry for
a negative control; the baseline's uncaught crash is saved separately.

The first real worker disconnect crashed Postgres.js 3.4.9 at `socket.write(null)`.
Upstream [issue 1208](https://github.com/porsager/postgres/issues/1208) and
[issue 1248](https://github.com/porsager/postgres/issues/1248) document the same
failure and the related transaction-scope escape. The official fix is in
[v4](https://github.com/porsager/postgres/commit/06cf284); registry verification
found no later 3.x release. A tracked `pnpm patchedDependencies` backport retains
3.4.9 instead of adopting the new major's parameter-typing/API changes.
It guards closed sockets, resets stale connection state, rejects statements from
lost/finished transactions, protects released connections, and handles type-fetch
rejections. ESM and CommonJS receive the same changes. The patch preserves the
Unlicense; no new dependency or ORM is introduced.

The auth fallback join also printed raw Drizzle errors directly to stderr before
application error handling. A one-line tracked `@better-auth/core` patch replaces
that direct console call with the configured logger and constant
`Database query failed`, then rethrows the original error. Its MIT licence is
unchanged. Both Dockerfiles copy tracked patches before the frozen installation.

The final isolated faults establish: API backend termination returns sanitized
500 and recovers to 200; a slow blocked query finishes after client abort and lock
release; worker retry completes on attempt two with exactly one digest and one
Inbox item; Valkey outage and OOM reject MCP calls with 429 and recover to normal
invalid-token 401; delayed work survives restart; API/worker SIGTERM exits zero
and leaves zero workload SQL sessions. A canary user ID and test email are absent
from API logs. ESM/CommonJS driver probes reject escaped transaction statements,
retain zero probe rows and reuse the pool after a disconnect. A real unpatched
negative control exits with the observed null-socket exception.

The client-abort assertion establishes eventual release after the injected lock is
released; it does **not** establish immediate PostgreSQL cancellation. No query or
lock timeout is configured by the shared pool. An indefinite external lock can
still occupy a slot until the lock is released or the process is stopped.
